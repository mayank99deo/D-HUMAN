## In one minute

1. **Two small ledgers and one thread table.**
   - `ask_days` holds each person's count for an IST day. It holds counts only, no text.
   - `ask_totals` holds everyone's count for the day. It drives the spend circuit breaker and holds no personal data.
   - `ask_turns` holds the questions and answers.
   - Deleting questions or reports touches only `ask_turns`, so it can never reset a count. This is the fix the reads cap needs too (Open items).
2. **The claim is one transaction that locks the person's counter row first:**
   - parallel requests take turns;
   - only one question per person can be in flight;
   - the 6th question can't get through.
   - **Proven on a real Postgres 17 server:**
     - 50 parallel questions from one person: exactly 1 in flight;
     - 20 workers racing: exactly 5 answered;
     - 40 people racing a breaker of 60: exactly 60 calls;
     - no deadlocks.
3. **What counts:**
   - Any answer the person sees uses a question, off-topic replies included. An off-topic call costs about two-thirds to four-fifths of a real answer.
   - Urgent and crisis replies are written in code and don't count.
   - Failures, timeouts and refusals hand the question back.
   - A second counter caps model calls at 10 a person a day, so failures can't be farmed.
4. **IST for everyone,** worked out from the server's clock. A profile's time zone can't open a new day: the meal limit has that hole today, but Ask doesn't. The day resets at 18:30 UTC.
5. **The breaker:**
   - `ASK_DAILY_MAX` counts model calls across everyone. It defaults to 2,000 a day, about $3 at worst-case size, and `0` switches Ask off.
   - When it trips, people see "Ask is resting until midnight (IST)", and their own count isn't touched.
   - The founders get one email at 80% and one at the cap.
6. **Retention:**
   - **Recommended:** today only. The daily job deletes questions and answers after the IST day, by about 10:30 IST the next morning.
   - **Kept:** counts and kinds, never words.
   - **Other deletes:** account deletion takes everything. A report delete blanks the answers that used report data and keeps the questions.
7. **Migration `0011_ask`:**
   - three tables with row-level security on, plus `profiles.ask_consent_at`;
   - safe to run twice;
   - tested in 4 orders on fresh embedded databases;
   - matches drizzle-kit's snapshot column for column.
8. **The route:** Node in `bom1` (from `vercel.json`; Cache Components forbids a `runtime` export), `maxDuration = 30`, a 20 s total AI deadline, Origin checks, `cache-control: no-store`, and no question text in any log.
9. **Context:**
   - **Query count:** one parallel batch of 5 indexed queries after the session and profile.
   - **Database time:** about 10 sequential round trips in all, around 10 to 40 ms in-region (inferred), against 2 to 5 s for Haiku.
   - **Shared web caches stay out:** no event searches and no brand lookups.

## 1. The daily limit

### 1.1 Why not reuse the `usage` ledger
`usage` fits a different job:
- it counts uses against a plan;
- it keeps them forever;
- `claimUseIn` applies the plan's rules under an advisory lock.

Ask needs three things it doesn't have:
- a per-day count;
- a separate cap on model calls;
- an everyone-wide counter, which would mean counting all of today's rows on every question.

Mixing them would also put a daily purge next to the billing ledger. So Ask gets its own two small counter tables.

### 1.2 The tables (full SQL in Appendix A.1)

| Table | Key | Holds | Personal data? | Kept |
| --- | --- | --- | --- | --- |
| `ask_days` | (user_id, day) | `used` (counts toward the 5), `attempts` (model calls started, never goes down) | Counts tied to a person | Until the daily purge after the day |
| `ask_totals` | day | `attempts` (model calls started, everyone), answered, off_topic, doctor, urgent, crisis, input and output tokens, cost in millionths of a dollar | No | For good (one row a day) |
| `ask_turns` | id (server-made) | The question, the answer, the safety notice, link ids, language, the kind, whether it counted, the report used, tokens, timing | Yes: health data | Section 3.2 |

`day` is always the IST date, `YYYY-MM-DD`.

### 1.3 The claim: one transaction, four statements
Lock order is always the same: the person's `ask_days` row, then a new turn, then the shared `ask_totals` row. Two orders can't cross, so the claim can't deadlock; the mixed parallel test showed none.

1. **Hand back dead questions.**
   - What: delete this person's turns still `pending` after 45 s, and lower `used` by that many on their day.
   - Why 45 s is safe: no live call is that old, because the route stops at 30 s.
2. **Count the person.**
   - What: `INSERT … ON CONFLICT (user_id, day) DO UPDATE SET used = used + 1, attempts = attempts + 1 WHERE used < 5 AND attempts < 10 RETURNING used, attempts`.
   - Locking: this locks the row. A parallel claim for the same person waits here until this one commits, then sees the new numbers.
   - No row back: the claim is refused (`limit` when `used` is 5, otherwise `too_many_tries`).
3. **Insert the question, if none is in flight.**
   - What: `INSERT … SELECT … WHERE NOT EXISTS (a pending turn of theirs from the last 45 s)`.
   - No row back: `busy`.
   - A repeated `client_key` breaks the unique index: `duplicate`, and the route then looks the turn up (section 5.4).
4. **Count everyone.**
   - What: the same conditional upsert on `ask_totals` with `attempts < ASK_DAILY_MAX`.
   - No row back: `paused`.
   - Why last: the hot shared row stays locked for one round trip, until COMMIT.

Any refusal rolls the whole transaction back, so a refused question changes no count and leaves no turn behind. A person refused by the breaker keeps their own count. That matters: if the global count went first, one person hammering refused requests could trip the breaker for everyone.

**Round trips:** BEGIN, the four statements, COMMIT: 6, at a few ms each in-region (inferred).

### 1.4 Completing, and handing back
- **Complete** is one statement (Appendix A.2):
  - It marks the turn answered **only if** it's still `pending` and no report delete has touched it (`removed_at is null`).
  - It lowers `used` by one when the kind doesn't count.
  - It adds the outcome to `ask_totals`.
  - Lock order is the turn, then the person's row, then the shared row. The claim never waits on a turn row (its in-flight check is a plain read), so this can't deadlock with it.
- **Release** is one statement:
  - It deletes the turn **if still pending** and lowers `used` by one.
  - It's safe to run twice: the second run finds no pending turn and changes nothing.
  - `attempts` never goes down.
- **The route's rule:** `finally { if (!saved) await releaseAsk(...) }`, as `app/api/food/route.ts:61-78` does for meals.
- **When nothing is released:** if the function is killed before `finally` runs, step 1 of the person's next claim hands the question back.

### 1.5 What counts (recommendation)

| Outcome | Model called? | Uses one of the 5? | Adds to `attempts`? | Turn kept? |
| --- | --- | --- | --- | --- |
| `answer` | Yes | Yes | Yes | Yes |
| `off_topic` | Yes | **Yes (recommended)** | Yes | Yes |
| `doctor` | Yes | Yes | Yes | Yes |
| `urgent`, caught by code before the model | No | No | No | Yes, with the fixed notice |
| `urgent`, raised by the model | Yes | No (handed back on completion) | Yes | Yes |
| `crisis`, caught by the word list | No | No | No | Yes, no AI text |
| Model refusal | Yes | No (released) | Yes | No |
| `max_tokens`, schema failure | Yes | No (released) | Yes | No |
| Network error, timeout, Anthropic 429 or 5xx | Maybe | No (released) | Yes | No |
| Report deleted mid-call | Yes | No (released) | Yes | No |
| `limit`, `busy`, `paused`, `rate_limited`, offline | No | No | No | No |

**Off-topic counts. The cost reasoning:**
- **Where the cost is:** almost all of it is the input: the fixed system prompt, the person's context and the question. An off-topic redirect pays all of that.
  - **Worst-case sizes** (the threats spec): about 9,000 tokens in. An answer is about $0.0014, and a redirect with about 60 tokens out is about $0.00093, so 66%.
  - **Typical sizes** (my guess until the AI efficiency lead measures): about 5,000 in. An answer is about $0.00065 and a redirect about $0.00053, so 80%.
- **If redirects were free:** they'd be a loophole that needs its own cap, and the counter people see would stop meaning what it says.
- **Mayank can change this cheaply.** If he decides redirects are free, it's one line in the policy constant (`ASK_COUNTED_KINDS`), with no schema change. The `attempts` cap of 10 already bounds the spend.

**Failures are handed back (Mayank's rule), and `attempts` bounds farming:**
- **The worry** (threats spec M7): if failures are free, someone could make the model fail on purpose and get unlimited calls.
- **The bound:** the second counter allows at most 10 model calls a person a day, whatever happens. At worst-case size, that's 10 × $0.0014 = **$0.014 a person a day** for someone deliberately failing every call. That's the most a person can cost, and the breaker caps the total.
- **What people get:** they never pay for our errors.

### 1.6 Deletes can never reset the count
- **Where the count lives:** only in `ask_days`, which holds no text, so nothing has a reason to delete it before the day is over.
- **What deletes touch:** "Clear now", report deletes and the retention purge (for past days only) all act on `ask_turns`.
- **Account deletion** removes `ask_days` too, through the foreign key.
- **The trade-off:** a new account gets a fresh 5. Making that account costs an emailed code (capped at 10 a day per address) and onboarding, and the breaker caps the total.
- **Tested:** clearing every turn, then asking again, still gives `limit`.

### 1.7 The IST day boundary
- **The day key:** `istDay(now) = Intl.DateTimeFormat("en-CA", { timeZone: "Asia/Kolkata" })`, from the server's clock at claim time. It's the same formatter as `localDate` (`lib/platform/profile.ts:25`), but always IST.
- **Why not the profile's time zone:** it's set by the browser and can be changed by anyone through `POST /api/profile` (`app/api/profile/route.ts:28,67-71`). Today that lets the meal limit open a second "today" (threats spec E1, which I confirm). A fixed IST key closes that for Ask, with no rolling-window cap needed.
- **Stored with the question:** the day goes on the turn and the counter. Complete and release use the stored day, never the clock. A question claimed at 23:59:59 IST that fails at 00:00:03 gives back yesterday's question and leaves today's count alone.
- **`resetsAt`:** the next midnight IST, which is 18:30 UTC. IST has no daylight saving. Tested at 18:29:59.999Z, at 18:30:00Z and across a year end.
- **What people see:** "midnight (IST)". The UI can also show `resetsAt` in the person's own time for people outside India.
- **The breaker** uses the same day.

## 2. Abuse limits beyond the daily 5

| Limit | Value | Where | What the person sees |
| --- | --- | --- | --- |
| Request body | 4 KB, refused before parsing (`Content-Length`, then a capped read) | Route | 413 `too_large` (the UI can't send this) |
| Question length | 300 code points (the UX spec's limit) and 2,000 UTF-8 bytes. Refused, never cut. Cleaned first (NFKC, controls and invisible characters out; threats spec D3) | `cleanQuestion()` | 400 `too_long` or `empty` |
| One in flight | One pending question per person, checked under the row lock | Claim, step 3 | 409 `busy`; "Still answering your last question." |
| Burst | In-memory 6 a minute per person, 30 per 10 minutes per IP (`allowRequest`, `lib/waitlist/rate-limit.ts:8`) | Route | 429 `rate_limited`; same copy as `busy` |
| Model calls | 10 a person a day, failures included | Claim, step 2 | 429 `too_many_tries`: "Ask couldn't answer several times today. Try again after midnight (IST)." |
| Everyone | `ASK_DAILY_MAX` model calls a day (default 2,000; `0` switches Ask off) | Claim, step 4 | 503 `paused`; GET says `paused: true` |
| Outer backstop | A monthly spend limit on the Anthropic workspace | Claude Console (Mayank; I can't change it) | Every AI feature stops when reached, so set it well above normal use |

**Why the burst limit is only a speed bump:**
- It's kept in memory, so each server instance has its own count.
- The database caps are the real limit.
- What it saves is database work: the stress test showed a script spinning on `busy` runs a transaction every time.
- **A cheap fix the route should use:** it already loads today's thread before the claim, so it can answer `busy` from that load when a fresh pending turn is there. That costs nothing extra and keeps the transaction for real attempts.

**Free turns:** urgent caught before the model and crisis replies cost no AI. They insert a turn directly with `counted = false`, without a claim. Only the burst limit guards them, which is enough: they spend no money, and the purge clears them daily.

**The breaker in detail:**
- **What it counts:** model calls started, not answers, because a failed call can still spend tokens.
- **The default:** 2,000 a day.
  - At the threats spec's worst case ($0.0014 a call) that's about **$2.80 a day**. At a typical $0.0007 it's about $1.40.
  - That's 400 people using all 5, which is plenty for launch.
  - Mayank sets the real number (decision 3).
- **Alerts:**
  - **When:** one email at 80% (the claim that reaches `ceil(0.8 × max)`) and one when a claim is first refused.
  - **How:** through `sendFounderAlert` (`lib/email/send.ts:595`), sent from `after()`.
  - **Once a day each:** a `job_runs` marker (`alert:ask-80:<day>`, `alert:ask-cap:<day>`), in the same pattern as `capAlert` (`lib/email/jobs.ts:889-911`). The emails count in the `founder_alert` budget stream.
  - **What the email says:** the count, the cap, and "raise `ASK_DAILY_MAX` in Vercel and redeploy if this is real use".
- **What people see when it trips:**
  - **The words:** "Ask is resting until midnight (IST). Your questions for today aren't used up." That's the threats spec's "Ask is resting until tomorrow", made exact.
  - **Nothing is called:** no model call and no count.
  - **The box:** GET's `paused: true` lets the UI say so before anyone types.
  - **Next day:** it reopens at midnight IST without a redeploy, because the counter is per day.

## 3. Storage and privacy (DPDP Act)

### 3.1 What is stored
- **`ask_turns`:** the cleaned question; the AI answer (null for urgent and crisis, whose words are code); the safety notice (fixed words plus marker names); link ids (never URLs); answer language; kind; whether it counted; the id of the report whose markers were in the pack; when a report delete removed the answer; model, tokens, milliseconds; times.
- **Never stored:** the context pack, the prompt, the model's raw output, IP addresses, the browser's user agent.
- **`ask_days` and `ask_totals`:** counts only.

### 3.2 Retention (recommendation: today only)
- **The keep:** `ASK_KEEP_DAYS = 0`, a code constant, not an environment variable. The privacy text and the UI's "Questions clear after today" line must change with it, so it shouldn't change silently.
- **When rows go:** the daily job deletes every `ask_turns` and `ask_days` row from before today (IST).
  - The job runs at about 10:30 and 19:30 IST, so a day's thread sits on the server until about 10:30 the next morning, roughly 10.5 hours past midnight.
  - People see only today's thread.
  - Hobby crons are best effort and can skip a run, so the worst case is about a day longer.
- **Why today only:**
  - The purpose is answering and showing today's follow-ups, and it ends with the day.
  - It's the least health data held, and it matches the UX spec.
  - It needs no new privacy line beyond "cleared after the day".
- **What quality review gets instead:** daily counts by kind, tokens, cost and failures, with no words.
- **The trade-off:** if someone reports a bad answer the next day, the text is gone.
- **If Mayank wants a review window:** 7 days. Then:
  - the privacy text gets a line, and the footer copy changes;
  - only Mayank reads them, and only to look into a reported answer.
  - It's a change of the constant, nothing else.
- **Copies we don't control:**
  - Database backups keep deleted rows until they expire; check the Supabase plan.
  - Anthropic handles API data under its own terms. As the threats spec says, promise only what D-Human does.

### 3.3 Deletes
| Action | `ask_turns` | `ask_days` | `ask_totals` |
| --- | --- | --- | --- |
| "Clear now" (`DELETE /api/ask`) | Answered turns deleted; one in flight stays | Unchanged | Unchanged |
| A report delete (`deleteReports`) | Every turn that used report data (`report_id` not null) has its answer, links and notice blanked, and `removed_at` set. The question stays (the person wrote it). | Unchanged | Unchanged |
| Report deleted mid-call | Complete finds `removed_at` set and saves nothing; release deletes the turn and gives the question back; 409 `report_deleted` | Question handed back | `attempts` kept |
| Account deletion (Settings, "Delete everything") | All, by foreign-key cascade on `user_id` | All, by cascade | Unchanged (no personal data) |
| Daily purge | Before today | Before today | Unchanged |

**Why report deletes blank every answer that used a report:**
- **Why not just that report's answers:** the pack holds only the newest report. But a follow-up answer can quote an earlier answer through the thread history (up to 2 to 4 earlier pairs), and that earlier answer may have used a different report.
- **Why "any report" is safe:** answers given with no report in the pack can't contain markers, so blanking every turn with a `report_id` is the simplest rule that's sure.
- **Matching the other specs:** it gives the threats spec's "Ask content goes with any report" (D12) and the UX spec's "Answer removed with the report it used" (§9) together.
- **Why `report_id` has no foreign key:** a cascade would delete the question. A set-null would lose which turns to blank before the update ran.

### 3.4 Who can read each column
- **Supabase's public Data API:** row-level security is on with no policies, so it returns nothing. Tested with a non-owner role.
- **The app:** connects as the tables' owner, so the code's `user_id` filter is the only guard between people. Every Ask query takes the user id from the session, never from the request (section 8 tests this).

| Columns | Who can read them |
| --- | --- |
| `ask_turns` question, answer, notice, links, lang, report_id | The person, through GET `/api/ask` (their own rows, today's day). Anyone with Supabase dashboard access (Mayank). Never: logs, emails, the Sheet, Analytics, wraps, other people. |
| `ask_turns` model, tokens, ms, kind, counted | The same, and they're summed into `ask_totals` |
| `ask_days` | The server (for `left`) and the dashboard |
| `ask_totals` | The server and the dashboard; no personal data |
| `profiles.ask_consent_at` | As the rest of the profile |

### 3.5 Logs
- **Never log** the question, the answer, the pack, a marker, a medicine or a meal title.
  - `logUsage("ask", message, t0)` (`lib/ai/client.ts:59`) already logs only tokens, cost and time.
  - The route adds one line: `[ask] kind=doctor counted=1 left=3 ms=2140`. There's no user id either.
- **Errors log their class name and HTTP status only** (`[ask] failed APIConnectionTimeoutError`).
  - Never log the error object or its message: a failed structured-output parse can carry the model's text (threats spec 2.3).
  - The same goes for database errors, which can echo parameter values.
- **The question travels only in the POST body,** never in a URL, so it can't reach Vercel's request logs, Analytics or a sign-in `?next=`.
- **Responses:** every one sends `cache-control: no-store`. Nothing in the Ask path uses `use cache`, `unstable_cache` or `cacheLife`.

### 3.6 The DPDP points (legal calls stay with Mayank and a qualified person)
- **Purpose:**
  - The consent step promises use "only to give you your reads, your food notes and your stack" (`components/platform/Onboarding.tsx:487`). Answering questions is a new purpose.
  - The threats spec (2.5, M1) and the UX spec (§18 Q3) both recommend a consent line for new users and a one-time notice for existing ones.
  - The data side is ready: `profiles.ask_consent_at` is in migration `0011`. Until it's set, the route answers 409 `consent_needed`, and `POST /api/ask/consent` sets it.
  - If Mayank decides the existing wording is enough, the column stays unused and the check is left out.
- **Minimisation:** the pack follows the threats spec's allowlist (D4): no email, no names, no city, no ids, no web-search text.
- **Retention:** section 3.2.
- **Erasure:** "Clear now", account deletion, report deletes.
- **Adults only:** an under-18 birth year gets 403 `adults_only` (threats spec M10). It's a check in code, with no query.

## 5. The route: `app/api/ask/route.ts`

### 5.1 Runtime, region, timeouts
- **Runtime:** don't export `runtime`. Cache Components forbids it, even `'nodejs'` (Next 16 docs, `runtime.md`). Node is the default.
- **Region:** don't export `preferredRegion` (deprecated). Functions run in `bom1` from `vercel.json:3`.
- **`export const maxDuration = 30`.**
- **The AI call:**
  - Each attempt has `timeout: 12_000` and `maxRetries: 1`.
  - One overall `signal: AbortSignal.timeout(20_000)` bounds both tries together, so the call ends by 20 s, including retry backoff.
  - The pattern is `MEAL_DEADLINE` (`lib/ai/food.ts:46`), tighter.
- **The budget:**
  - Session, profile and the context batch take about 50 ms (inferred).
  - The claim and saving the answer take about 20 ms.
  - The AI call takes at most 20 s.
  - That's 21 s at worst, leaving 9 s spare for a cold start before the 30 s limit.
- **The client:** wait 25 s (`send(…, { timeoutMs: 25_000 })`; the default is 20 s, `components/platform/net.ts:9`).
  - If no reply comes, call GET. The answer is saved server-side even when the browser gave up, so GET shows it.
  - If the turn is still pending, poll GET every 2 s until it settles, which is at most about 10 s more.
- **GET:** no AI. A plain request-time handler, since `apiUser()` calls `connection()` first.

### 5.2 POST, in order (cheap checks first)
1. `sameOrigin(request)`, else 403 `bad_origin` (`lib/auth/origin.ts:13`). No database.
2. Body over 4 KB: 413 `too_large`.
3. `apiUser()`, else 401 `signed_out`.
4. Burst limits: 429 `rate_limited`.
5. Parse `{ id, question }` with zod. `id` is the browser's UUID for the question and becomes `client_key`.
   - Then `cleanQuestion`: 400 `invalid`, `empty` or `too_long`.
6. `aiMode() === "off"`: 503 `ai_off`. `askDailyMax() === 0`: 503 `paused`.
7. `getProfile`: 409 `not_onboarded`. Under 18: 403 `adults_only`. No `ask_consent_at` (if adopted): 409 `consent_needed`.
8. The crisis word list (threats spec D7) matches: save a free turn and return `kind: "crisis"`. No claim, no AI.
9. The context batch (section 6), in parallel. From today's thread it settles three things:
   - an answered turn with this `client_key`: 200 with the saved turn, counting nothing;
   - a pending turn with this `client_key`: 409 `busy`;
   - any other fresh pending turn: 409 `busy`.
10. The code floor before the model (threats spec D7) says urgent: save a free turn with the fixed notice and return `kind: "urgent"`.
11. **Claim** (section 1.3). The refusals:
    - `limit`: 200 with `kind: "limit"`, `turn: null`, `left: 0`, `resetsAt`.
    - `too_many_tries`: 429.
    - `busy`: 409.
    - `paused`: 503, plus the alert from `after()`.
    - `duplicate`: look the turn up and answer as in step 9.
12. Call the model (mock or live). Then the floor after the model, the filters and the link ids (threats spec D7 to D9).
13. **Complete**, with `counted` from the policy. If it saves nothing, the report was deleted mid-call: release and answer 409 `report_deleted`.
14. On any failure: **release** in `finally`, then answer 502 `failed`, 504 `timeout`, 422 `refused` or 500 `error`, always with `left`.
15. `after()`: the 80% alert when the claim's everyone-count reaches that line.

### 5.3 GET and DELETE
- **`GET /api/ask`:** session, profile (409 `not_onboarded`), then one parallel batch:
  - today's turns;
  - one statement for both counters (`used`, `attempts`, everyone's `attempts`);
  - the latest-report summary (ready or being read, flags, the printed name, `analyzed_at`);
  - the latest stack's `created_at` (for stale marking, threats spec D14).
  - It returns `{ turns, left, day, resetsAt, paused }` plus the UX spec's extra fields. Each extra comes from the same batch or from code: starters, pinned urgent and printed-for, report state, first use (`ask_consent_at` is null), region, `aiOff`.
  - `left = attempts >= 10 ? 0 : 5 − used`.
  - Pending turns older than 45 s are left out: they're dead and the next claim hands them back.
- **`DELETE /api/ask`:** Origin check and session. Deletes the person's answered turns and returns `{ cleared, left }`, with `left` unchanged.
- **`POST /api/ask/consent`:** only if Mayank adopts the notice. Origin check and session; sets `ask_consent_at` if it's null.

## 8. Test plan

**In `npm test`, on PGlite** (`tests/ask-ledger.test.ts`, extending the 16 checks already run in the prototype):
- **The limit:** 5 count, the 6th gives `limit`, and the refusal changes no count.
- **One in flight:** a second claim while one is pending gives `busy` and rolls back.
- **Release:** it hands back once; again, or after answering, it does nothing. Failures don't use questions, but the 11th call gives `too_many_tries`.
- **Kinds that don't count:** an uncounted kind is saved and hands back its question, and `attempts` keeps the call.
- **Client keys:** a repeated `client_key` rolls back; another person may use the same key.
- **Dead questions:** a pending turn older than 45 s is handed back by the next claim, which isn't `busy`.
- **Deletes don't reset the count:** clearing every turn and blanking for a report both leave the count alone.
- **A report deleted mid-call:** nothing is saved, and the question goes back.
- **The breaker:** refused people keep their count and leave no turn; it's per IST day.
- **Totals:** calls, answers by kind, tokens and cost.
- **The purge:** before today goes, today stays.
- **Account deletion:** cascades turns and counts; totals stay.
- **The IST boundary:** 18:29:59.999Z, 18:30:00Z, `resetsAt`, and a year end.
- **Query plans:** the thread, in-flight, client-key and purge queries use their indexes.

**`tests/ask-route.test.ts`** (route with stubs, in the pattern of `tests/billing.test.ts`):
- **Each code in 5.4,** with its status and whether it used a question.
- **Another person's thread is never readable:**
  - two people, each with turns;
  - GET as A returns only A's;
  - DELETE as A leaves B's;
  - a POST from A with B's `client_key` is a new question for A and never returns B's turn;
  - `askContextData(A)` never holds B's markers, even when B's report id is passed.
- **The canary:** a unique string in the question, pack and stubbed answer never appears in any `console` output, including on every error path (threats spec 2.3).
- **Headers:** `cache-control: no-store` on all three methods.
- **The Origin check** on POST and DELETE.
- **Gates:** under 18 is refused; `consent_needed` applies before consent.
- **Failures:** a stubbed model that throws `APIConnectionTimeoutError` gives 504 and `left` unchanged. One that throws a parse error gives 502 and `left` unchanged.
- **A report deleted between claim and save** gives 409 `report_deleted` and `left` unchanged.
- **Replay:** the same `id` twice gives the saved turn and `left` unchanged.

**`tests/migrations.test.ts` additions:** section 4.

## 11. Decisions for Mayank

1. **Do off-topic replies use one of the 5?**
   - **Recommendation:** yes (1.5). It's one constant either way.
2. **Do model refusals and failures use a question?**
   - **Recommendation:** no, as you asked, with the 10-calls-a-day cap.
   - This disagrees with the threats spec's M7, so you choose.
3. **`ASK_DAILY_MAX`:**
   - **Recommendation:** 2,000 model calls a day (about $2.80 at worst-case size) to start, raised at the 80% alert.
   - Also set a monthly spend limit on the Anthropic workspace in the Console (you, not code).
4. **How long to keep questions:**
   - **Recommendation:** today only.
   - **The alternative:** 7 days, read only by you to look into a reported answer. That needs a privacy line.
5. **The Ask notice and consent line** (the threats spec's M1, the UX spec's Q3):
   - **Recommendation:** yes. The column is in the migration either way.
   - Whether a notice is enough for existing users, or they must agree again, is a legal call.
6. **Ask's day is IST for everyone,** as you said. People outside India reset at midnight IST, which is shown in their own time.
   - **Related, for meals:** the meal limit can be dodged by changing the profile's time zone (threats spec E1). The same fixed-day key would close it, but it would move the meal day for anyone outside India.
7. **Pick the newest report by collection date** for Ask now, and for Home, Wraps and Stack next (the threats spec's M11; an Open item).
8. **Anthropic rate limits:** check the organisation's Haiku limits in the Console before launch, so a busy hour doesn't turn into failed answers.

### A.2 The ledger statements (tested; section 0)
Parameters are numbered. The build lane can keep these as `sql` templates, or use drizzle's `onConflictDoUpdate({ target, set, setWhere })` for the two upserts.

**Claim** (one transaction, in this order):
```sql
-- 1. Hand back this person's questions that died mid-call. $1 user, $2 45 (seconds).
WITH dead AS (
  DELETE FROM ask_turns WHERE user_id = $1 AND status = 'pending' AND created_at < now() - make_interval(secs => $2) RETURNING day
), per_day AS (SELECT day, count(*)::int AS n FROM dead GROUP BY day)
UPDATE ask_days d SET used = greatest(d.used - per_day.n, 0) FROM per_day WHERE d.user_id = $1 AND d.day = per_day.day;

-- 2. The person. No row back: refused ("limit" when used = 5, else "too_many_tries").
INSERT INTO ask_days (user_id, day, used, attempts) VALUES ($1, $2, 1, 1)
ON CONFLICT (user_id, day) DO UPDATE SET used = ask_days.used + 1, attempts = ask_days.attempts + 1
WHERE ask_days.used < 5 AND ask_days.attempts < 10
RETURNING used, attempts;

-- 3. The question, when none is in flight. No row back: "busy". Unique violation: "duplicate".
INSERT INTO ask_turns (id, user_id, client_key, day, question, report_id)
SELECT $1, $2, $3, $4, $5, $6
WHERE NOT EXISTS (SELECT 1 FROM ask_turns WHERE user_id = $2 AND status = 'pending' AND created_at > now() - make_interval(secs => 45))
RETURNING id;

-- 4. Everyone. No row back: "paused". $2 is ASK_DAILY_MAX (checked > 0 before the transaction).
INSERT INTO ask_totals (day, attempts) VALUES ($1, 1)
ON CONFLICT (day) DO UPDATE SET attempts = ask_totals.attempts + 1
WHERE ask_totals.attempts < $2
RETURNING attempts;
```
Step 3 looks only at pending turns from the last 45 s, so a dead turn can never block a new question.

**Complete** (one statement):
```sql
WITH done AS (
  UPDATE ask_turns SET status = 'answered', kind = $3, counted = $4, answer = $5, notice = $9, links = $10, lang = $11,
    model = $12, input_tokens = $6, output_tokens = $7, ms = $13, answered_at = now()
  WHERE id = $1 AND user_id = $2 AND status = 'pending' AND removed_at IS NULL
  RETURNING day, counted
), refund AS (
  UPDATE ask_days d SET used = greatest(d.used - 1, 0) FROM done
  WHERE NOT done.counted AND d.user_id = $2 AND d.day = done.day RETURNING 1
)
UPDATE ask_totals t SET answered = t.answered + 1,
  off_topic = t.off_topic + (CASE WHEN $3 = 'off_topic' THEN 1 ELSE 0 END),
  doctor    = t.doctor    + (CASE WHEN $3 = 'doctor'    THEN 1 ELSE 0 END),
  urgent    = t.urgent    + (CASE WHEN $3 = 'urgent'    THEN 1 ELSE 0 END),
  crisis    = t.crisis    + (CASE WHEN $3 = 'crisis'    THEN 1 ELSE 0 END),
  input_tokens = t.input_tokens + $6, output_tokens = t.output_tokens + $7, cost_micros = t.cost_micros + $8
FROM done WHERE t.day = done.day
RETURNING t.day;   -- no row: nothing was saved (a report delete reached it): release, then 409 report_deleted
```

**Release** (one statement; safe to repeat):
```sql
WITH gone AS (DELETE FROM ask_turns WHERE id = $1 AND user_id = $2 AND status = 'pending' RETURNING day)
UPDATE ask_days d SET used = greatest(d.used - 1, 0) FROM gone WHERE d.user_id = $2 AND d.day = gone.day;
```

**Report delete** (inside `deleteReports`' transaction, when any report went):
```sql
UPDATE ask_turns SET answer = NULL, links = NULL, notice = NULL, removed_at = now()
WHERE user_id = $1 AND report_id IS NOT NULL AND removed_at IS NULL;
```

**Clear now:** `DELETE FROM ask_turns WHERE user_id = $1 AND status = 'answered'`.

**Purge** (daily job; `$1` is today's IST date minus `ASK_KEEP_DAYS`):
`DELETE FROM ask_turns WHERE day < $1` and `DELETE FROM ask_days WHERE day < $1`.
